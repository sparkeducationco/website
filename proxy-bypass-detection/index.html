Beyond the URL.

01

Why a new URL can defeat an old blocklist

A URL blocklist identifies known destinations. A browser proxy can move to a different hostname or path while continuing to run similar software. If a filter only knows the previous address, the new deployment may remain available until its list is updated.

Schools still need website rules and allowlists. Detecting the proxy software adds another source of evidence when the address alone is not enough. It is especially useful to evaluate when students repeatedly find new addresses for the same type of workaround.

02

How Spark looks for browser proxies

Spark inspects browser and traffic signals for supported proxy protocols and runtimes. Its detectors include Wisp, TompHTTP Bare, Scramjet, Ultraviolet, and Rammerhead. Depending on the tool, evidence can come from protocol behavior, runtime signals, or recognizable script structures.

These checks look for evidence of supported proxy implementations. They do not rely solely on a site's name containing “proxy.” When the evidence meets a detector's criteria and district policy permits blocking, Spark redirects the affected browsing activity to its block page.

Detection is not a guarantee that every proxy will be caught. New implementations, changed code, and tools that conceal the expected signals can evade a detector. Districts should evaluate the actual tools and browsing conditions relevant to their schools.

03

How detection and website rules work together

Website rules handle known destinations. Browser detection helps identify supported tools as they run. District exceptions keep approved resources available. Each has a different role in managing access.

For example, blocking one known proxy address can stop repeat visits to that address. Detecting a supported proxy runtime can help with a new deployment that has a different address. Your team should test both cases rather than assuming a successful block proves coverage of all bypasses.

Spark operates in managed Chrome, including Chromebooks. It does not provide whole-network coverage or inspect every app on a device. See the Chromebook filtering and deployment guide for the browser's role in a district setup.

04

Evaluate detection without disrupting classes

Run a small pilot with examples approved by your technology team. Include ordinary educational websites as well as the proxy tools you want to evaluate. Test current versions, different deployment addresses, and the district exceptions your schools need.

  • Record whether each supported example is detected and blocked.
  • Check that legitimate classroom tools remain available.
  • Review the reported reason for a block before changing policy.
  • Verify that enrolled devices deliver the expected reports.
  • Document missed detections and unexpected blocks for follow-up.

Repeat relevant checks when the tools or your configuration change. A single demonstration cannot establish long-term detection accuracy.

05

Give administrators context for a block

For devices enrolled and configured to report, Spark provides blocked-activity information so district teams can inspect what happened. Reports include the site, device, time, and detection context. They describe blocked activity rather than a full browsing history.

Use that context alongside your district's approved-site policy. Review the privacy policy and discuss reporting access before rolling out to students.
